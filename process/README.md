## 2. 固定目录与命名

```text
process/
  README.md                         全局规则与需求索引
  templates/                        汇总、需求、计划索引/明细、任务看板/明细模板
  <需求名称>-<状态>/
    README.md                       需求/计划汇总：目标、基线、进度、问题及入口
    require/
      README.md                     需求、约束、验收
    plan/
      README.md                     计划索引、顺序及依赖摘要
      plan-<编号>-<名称>.md          单一目标的计划明细
    task/
      README.md                     本需求看板
      task-<任务编号>-<任务名称>.md  单项任务明细
```

- **MUST** 每次需求分析形成或更新对应 `require/` 文档，计划放同需求的 `plan/`，看板与任务放 `task/`；三类文档相互链接，不仅保留在对话中。
- **MUST** 计划与任务明细拆成小文件，一份围绕一个可说明目标、依赖和交付的内容；不以长篇单文件承载全部工作包。计划使用 `plan-<编号>-<名称>.md`，任务使用 `task-<任务编号>-<任务名称>.md`；编号含领域前缀，例如 `plan-wui-001-baseline.md`、`task-wum-001-contract.md`。名称使用稳定英文 `kebab-case`，不带负责人或执行状态。
- **MUST** `plan/README.md` 维护计划细项链接、总体顺序及依赖摘要，`task/README.md` 维护实际任务看板；两者不复制全部实施细节。公共契约只在一个权威文件定义，由各细项引用；不能为了拆文件复制多份契约，或机械按行数切断同一职责。
- 计划索引 ID 为 `PLAN-<领域>`，细项 ID 为 `PLAN-<领域>-<三位序号>`，任务 ID 延续 `<领域>-<三位序号>`；计划与任务是不同命名空间，不默认一一对应。一个计划可以拆成多个任务；公共计划说明文件不算新增执行工作包。迁移文件名不改变已交付任务 ID、状态或验收记录。
- **MUST** 独立需求使用独立目录、计划与编号。用户管理、拓扑集成、现有 Web 体验优化分别维护；依赖通过链接表达，不把后续独立需求追加成已完成需求的实施任务。
- 名称采用稳定的英文 `kebab-case`，例如 `web-ui-optimization`；状态后缀独立变化。根 `README.md` 是本需求唯一的需求/计划汇总，至少记录 `feature`、`status`、`updated_at`、代码基线、进度、问题及三个入口；不另建重复维护的 `summary.md`。
- 需求、验收、计划、任务使用稳定 ID；拆分/迁移保留旧 ID 对应关系，旧编号不复用。路径规则见[命名规范](../docs/architecture/naming.md)。
- 模板：[汇总](templates/summary.md)、[需求](templates/require.md)、[计划索引](templates/plan-index.md)、[计划明细](templates/plan.md)、[任务看板](templates/task-board.md)、[任务明细](templates/task.md)。汇总模板用于需求根 `README.md`；补充方案、设计或验收记录按职责放在本需求三个子目录内；架构规范等跨需求文档仍在 `docs/`。

## 3. 需求总体状态与目录迁移

| 目录状态 | 含义 |
| --- | --- |
| `draft` | 正在分析/规划，未进入实施；文档写完不代表功能完成 |
| `ready` | 范围与执行前置明确，尚未开始实施 |
| `in-progress` | 已认领并进入实施 |
| `blocked` | 整项需求受具体阻塞影响；注明原因和解除条件 |
| `in-review` | 实现及必要验证已交付，等待评审/验收 |
| `done` | 本需求范围的实现、验收与交付有实际证据 |
| `cancelled` | 需求取消，保留理由与历史编号 |

- **MUST** 目录后缀、根元数据与本索引一致。状态变化时整体重命名目录并同步所有相对链接、元数据路径和引用，不复制第二份活动目录。
- 总体状态不等于单个任务状态；任务明细继续使用 `backlog`、`ready`、`in_progress`、`blocked`、`in_review`、`done`、`cancelled`。不能因单个任务完成或计划成文把需求改为 `done`。
- 已完成需求的文字澄清不自动重开开发；新增独立目标另建目录。确需修复同一需求时按实际范围重开并保留历史交付证据。
- 原有未提交内容必须保留。本次用户管理以已交付分支的14项任务与验收为事实源；原文档工作区的未提交草案保留在其 `require/history/`、`plan/history/`、`task/history/`，明确为历史，不能据其旧状态重做实现。

## 4. 先汇总，再依据项目现状展开明细

### 4.1 固定顺序

**“需求拆分”的默认含义：** 用户说“需求拆分”或对指定需求说“开始拆分”时，必须完成“需求文档 → 小需求计划 → 小任务”的完整文档链路，并同步根汇总、计划索引和任务看板。已有计划经代码/现状复核后复用，不重复建同义计划；不能只写目录、计划级工作包或泛泛待办就交付。用户明确只要需求分析或计划时，以其限定范围为准。拆分完成不代表认领、实施或测试已发生。

1. **读取现状**：先读适用规范、已有需求汇总、相关明细、工作区状态和受影响源码。记录文档所在分支/提交、实施所依据的分支/提交、核查日期及相关未提交变化；两者不同时明确区分，不能将当前分支缺失误判为交付分支未实现。
2. **先写汇总**：新建或更新本需求根 `README.md`，说明目标、范围、已核实基础、文档与实现进度、问题/阻塞/待确认项及下一步。首次信息不足时先列待核实事项，不用猜测补齐。
3. **按汇总展开**：根据汇总目标、事实依据和依赖，编写/修改 `require/`，建立 `plan/README.md` 的细项目录，再逐项写 `plan-<编号>-<名称>.md`；“需求拆分”必须继续创建对应 `task-<任务编号>-<任务名称>.md` 并登记看板。每项任务能追溯到具体计划、需求/验收 ID、代码依据及现有边界。信息不足时先建立核实任务，后续任务写明启动条件和待决边界，不编造实现细节，也不把它们冒充已就绪。仅要求计划时不强制继续拆任务；拆文档均不擅自进入实现。
4. **发现变化及时回写**：细化或执行中发现新的事实、范围调整或阻塞，先更新汇总对应条目，再调整受影响明细；本次交付前核对汇总、计划、看板与任务一致。已完成历史记录保留原验证时间和范围，不因本次修改重新宣布验证通过。

这一顺序适用于新建和后续修改需求、计划、任务；不额外引入用户审批。待核实项只影响相应结论与依赖任务，其余已明确范围可继续推进。

拆分交付前必须核对：每个本期计划都有任务映射或明确的公共说明/后置理由；任务不是计划标题的简单复制，而是有独立输入、输出、写入范围和完成条件的工作。已生成但未认领的任务默认 `backlog`、`owner: null`；只有前置与证据充分时才转为 `ready`，不得因文件生成就记为完成。需求仍有待核实的实施前置时保持 `draft`，并说明具体问题。

### 4.2 汇总的必填内容

| 内容 | 最低要求 |
| --- | --- |
| 目标与范围 | 用户目标、当前阶段、关键边界；独立需求单独汇总 |
| 基线与现状依据 | 分支、提交、核查日期、相关未提交变化；实际代码路径及符号/入口、结论和核实范围 |
| 进度 | 需求/计划/任务入口、文档进展、实现进度、下一步；文档写完不等于实现完成 |
| 问题与待确认项 | 稳定编号、来源/证据、影响及受影响任务、状态、下一步/解除条件、负责人（未知为 `null`） |
| 维护记录 | 本次变化与时间；解决问题保留结论和依据，防止后续重复排查 |

- **MUST** 进度源于实际文件、任务明细和交付证据；已完成/总任务数明确统计范围，取消项单列，无任务明细时写“尚未拆分”，不能把工作包数转换成完成率或虚构百分比。
- **MUST** 问题区分已遇问题、实际阻塞、待确认项及已解决事项。推测风险标为风险，不能写成已发生故障。未排查时写“尚未核查”；限定范围内未发现问题时写明范围，不无依据地写“无问题”。
- **MUST** 认领、状态变化、问题出现/解决、基线变化或范围调整时同步汇总。具体执行状态仍以任务明细为准，根汇总引用/汇集事实，不与看板建立两套独立状态。

### 4.3 具体内容必须有代码和项目依据

- **MUST** 对现有能力、缺口、复用点和依赖的判断，实际阅读相关调用链中的必要部分，例如页面/路由、API 调用与处理器、模型/迁移、配置和既有验证入口；不为写文档运行应用测试，也不要求无关的全仓扫描。只读到接口定义时不能声称调用端已接入或运行正常。
- **MUST** 依据记录到文件路径和关键符号、路由或配置项，并关联核查提交；行号可辅助定位。跨分支引用使用固定提交链接或明确的 worktree/提交来源。旧设计文档与任务完成记录可作历史依据，不能替代当前代码核实，也不能把历史验证当作本轮执行。
- **MUST** 分开标记“已核实事实”“用户约束”“拟新增方案”“待核实”。拟新增文件、接口、字段和命令注明尚不存在；未找到能力时记录查阅/搜索范围，只能得出该范围内未找到的结论，不能据此断言全项目不存在。
- **MUST** 每个具体方案或任务说明：对应需求/验收 ID、相关依据、现有行为/缺口、拟改内容、复用模块、写入范围及依赖。用户提出的新增目标不必已有代码实现，但其接入位置和现有边界必须有依据；不适用的项目说明原因。
- **MUST** 信息缺失、文档与代码冲突或外部项目不可用时，汇总中记录缺口、影响与核实方式；受影响结论保留待核实，不编造外部 API、状态机制、设备能力、排期、负责人或测试结果。实施基线变化后重新核对受影响证据。

## 5. 需求、计划与任务的事实源

1. **需求**：用户场景、对象与权限、范围、规则和可观察验收；不维护第二套执行状态。
2. **计划**：索引链接各小文件并表达执行顺序，具体方案、契约、前置、写入范围和完成条件放在对应计划明细；计划级工作包不能冒充已认领任务。计划明细至少有稳定 ID、汇总/需求入口、适用基线与依据、目标/边界、依赖和交付条件；公共契约通过链接引用。
3. **任务**：每个小文件具有 `id`、`feature`、`status`、`owner`、`depends_on`、`write_scope`、`requirements`、`acceptance`、`updated_at`，并链接具体计划明细。新拆任务同时填写 `summary`、`plans`、`read_scope`、`parallel_group`，并在正文记录公共写入与交接；无负责人用 `null`，无前置用 `[]`。明细是执行状态的事实源，协调者同步本需求看板。历史已交付任务不为补充新字段而重开实现。
4. **汇总与交接**：根 `README.md` 是编写入口与进度/问题概览，引用上述事实源；记录最终文件、契约、证据与限制。失败/阻塞说明原因，不将未实现、未执行、mock 或文档状态记为真实功能通过。

## 6. 并行与联调

- **MUST** 多 Agent 分析是每次需求拆分的必需步骤：先按真实模块、页面、契约及文件定位独立工作，再给出任务依赖图/表与批次。同一计划可拆多个任务，不强制计划与任务一一对应；不能仅复制工作包名称当任务拆分。
- **MUST** 优先按低耦合、文件不重叠、可独立验证的工作包拆分，明确唯一负责人、输入/输出契约、依赖和共享文件写入者。事务、状态与生命周期有真实依赖时顺序执行。
- **MUST** 每项新任务填写只读输入范围、独占写入范围、可并行组、串行前置、输出契约和接收任务；目录包含子路径，新增文件也计入占用。没有可并行空间时说明真实依赖，不伪造并行分组。
- `read_scope` 列额外的只读依赖；待修改文件只列入 `write_scope`，修改前同样必须读取，不重复列入 `read_scope`。这样既保留代码核查要求，也避免一个任务对同一文件同时声明只读和写入；未列入写入范围的依赖始终只读。
- `write_scope` 包括源码、测试、语言资源、模块注册、路由和脚本等实际范围。目录与子路径也算重叠；多个 Agent 可同时只读，同一文件只安排一个写入者。
- **MUST** 计划索引或看板列“公共文件 → 唯一写入任务 → 使用者 → 交接条件”。未分配执行者时仍确定写入任务，`owner` 保持 `null`；不能把“协调者”作为允许多个任务同时改文件的借口。共享类型/文案/脚本由指定任务交付，消费者提交需求、使用稳定契约，不抢写。
- **MUST** 跨需求也检查共享文件：拓扑与 Web 美化若涉及同一 `MainPage.vue`、`main.ts`、主题、语言资源或 API 客户端，协调者确定顺序和交接，不允许并行抢写。独立 worktree 不消除语义冲突。
- **MUST** 共享文件交接记录采用提交、契约版本、产出/验证证据和未解决问题；接收者先吸收前序改动并核对差异。并行期间消费者使用约定版本，读取方不应假定正在被修改的公共契约稳定。构建输出、预览实例、端口和测试数据也需隔离，不能多个 Agent 共写同一输出。
- 契约变更先更新对应需求/计划并通知消费者；任务变更同步看板。公共文件所有权不能由执行者自行扩大。
- 实现任务先完成自身构建与针对性验证，随后单独安排接线、联调和整体验收任务。联调列前置交付、隔离环境、成功/失败/权限/兼容场景、失败回派和退出条件。
- **MUST** 拆分完成前检查任务依赖无环、无悬空 ID；任何写入范围重叠都必须有可追踪的串行依赖或明确调度规则。遗漏代码、文档、语言资源、脚本或测试入口的写入范围均须补齐；根汇总/索引/看板和任务元数据由协调者集中同步，任务产物各有独立目录。
- 用户管理已完成，不作为再次开发的隐含前置。Web 美化可在已交付 Web 上独立开展，不等待未实现的拓扑、EasyADB、家居或导航能力。
