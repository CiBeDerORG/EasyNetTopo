# 产品设计思维与规范

适用于 Web 控制台、桌面/移动 GUI、配置生成器及 CLI 的用户可见行为。实现时同时遵守 [前端规范](frontend.md)、[后端规范](backend.md) 和 [命名规范](naming.md)。

本文中的 **MUST** 表示新功能和本次修改必须满足，**SHOULD** 表示通常应满足、偏离时在变更说明中解释原因，**MAY** 表示按场景选用。既有实现不自动视为合规，也不要求为无关修改批量改造历史界面。

## 1. 当前产品事实与适用边界

以下是仓库中的现有事实，后续条款是对新增和修改行为的规范要求：

- EasyTier 是去中心化异地组网产品；节点可以直连，也可以通过其他节点中继，见 [中文说明](../../README_CN.md)。不能将整个产品描述为必须依赖中心服务器。
- Web 控制台位于 `easytier-web/frontend`；GUI 位于 `easytier-gui`，共同使用 `easytier-web/frontend-lib` 的配置、状态等组件。
- 共享配置组件存在网络名称、网络密码和管理员签发凭据等身份配置；`Config.vue` 已区分共享密码与凭据模式。
- `Status.vue` 和 `modules/statusDisplay.ts` 展示节点、连接、路由、延迟与丢包等信息；这些值不能统称为同一种“连接状态”。
- 共享界面语言资源位于 `frontend-lib/src/locales/cn.yaml` 和 `en.yaml`；Rust/CLI 文案资源位于 `easytier/locales/app.yml`。现有语言代码 `cn` 是实现约定，不在本规范中改名。
- 移动端 VPN 有系统授权、原生运行状态和多个网络实例协调，见 `easytier-gui/src/composables/mobile_vpn.ts`；界面请求成功不等于 VPN 已运行。

## 2. 从用户任务推导方案

**PD-01 MUST**：先写清用户要完成的任务，再决定页面、按钮和参数。需求至少说明：谁在什么场景下，要获得什么可观察结果，以及当前障碍。

典型任务包括加入已有网络、创建网络配置、确认设备是否在线、诊断对端不可达、配置子网代理，以及安全地退出或撤销访问。不要把“增加一个字段”本身当成完整的用户目标。

**PD-02 SHOULD**：用最短的完整任务链组织流程：选择或创建配置 → 校验 → 保存/应用 → 观察运行结果 → 验证对端可达 → 必要时恢复。

**PD-03 MUST**：设计前确认操作对象及归属：本地配置、运行实例、远程设备、网络成员或管理员策略。文案与权限判断不得混用这些对象。

**PD-04 MUST**：新增持久化状态、跨端行为、权限、破坏性操作或多步骤流程时，在 issue、PR 描述或相邻设计文档中记录决策与验收。独立的小文案、间距或样式修复可以直接在 PR 中简述，不需要单独立项或审批。

**PD-05 MAY**：存在两种合理交互方案时，记录目标、限制和取舍；需要探索时再制作原型。不要仅为填写模板而增加无意义步骤。

## 3. 信息架构与渐进披露

**PD-06 MUST**：基本组网流程只要求当前身份模式及连接方式真正需要的参数。凭据模式与共享密码模式的要求要分别说明，不能暗示所有模式都必须填写网络密码。

**PD-07 SHOULD**：将 MTU、协议偏好、路由、代理、ACL、监听地址等高级能力按用户任务分组；提供简短用途、单位、有效范围和默认行为。保留需要精细控制的用户进入高级配置的路径。

**PD-08 MUST**：导入、编辑、保存和启动配置不得静默丢弃不认识的兼容字段。确实无法保留时，指出字段和影响，再提供明确的继续或返回路径。

**PD-09 MUST**：配置来源、只读限制和实际生效位置应可识别。由远端管理的配置不可伪装为本地可编辑；“保存”与“立即应用”应按真实行为命名。

**PD-10 SHOULD**：先展示可采取行动的状态摘要，再提供节点明细、路由、协议和日志。不要让内部结构、堆栈或序列化字段替代用户需要的结论。

## 4. 状态模型与操作反馈

**PD-11 MUST**：显式区分下列维度；可以使用独立字段或视图模型，不要求增加后端枚举或重写现有协议：

| 维度 | 必须能分辨的情况 | 不可推导的结论 |
| --- | --- | --- |
| 数据读取 | 未读取、读取中、已读取、失败、过期 | 读取失败不等于设备离线 |
| 配置 | 未保存、保存中、已保存、保存失败、待应用 | 保存成功不等于运行成功 |
| 实例 | 已停止、启动中、运行中、停止中、失败 | 进程运行不等于存在对端连接 |
| 节点连接 | 未连接、连接中、直连、中继、连接失败/断开 | 中继是可用路径，不能一律视作故障 |
| 业务连通性 | 未验证、验证中、可达、不可达 | 对端出现在列表中不等于子网业务可达 |

**PD-12 MUST**：成功反馈必须对应已确认的结果。后端仅接受异步请求时，展示“请求已提交”或“启动中”，在取得运行证据后再展示完成。

**PD-13 MUST**：轮询、事件订阅或远程连接中断后，保留最后已知数据时应标明其过期状态；无测量值使用“未知/暂无数据”等语义，不用 `0 ms`、`0%` 伪造健康指标。

**PD-14 MUST**：耗时操作提供可见反馈，并防止重复提交造成重复实例或重复授权。切换设备、网络或页面后，旧请求结果不得覆盖新选择的对象。

**PD-15 SHOULD**：对支持取消的操作提供取消入口；不支持取消时说明当前进度和后续操作。超时阈值应来自实际接口与平台能力，不在界面任意写死一个“通用成功时间”。

**PD-16 MUST**：移动端系统授权被拒绝或关闭时，应返回可理解的未启动状态及重试入口，不能持续旋转、自动反复弹窗或显示已连接。

## 5. 校验、错误与恢复

**PD-17 MUST**：输入校验同时解释“哪里有问题”和“如何修正”。地址、端口、CIDR、身份信息等错误应尽量关联到对应输入，保留用户未提交的非敏感内容。

**PD-18 MUST**：客户端校验用于及时反馈，授权和安全校验仍由后端承担。不得用禁用按钮或隐藏菜单替代服务端权限控制。

**PD-19 MUST**：错误反馈说明失败操作、可确认的原因和下一步。缺少权限、身份不匹配、超时、服务不可达、配置无效应能区分；原因未知时明确说明未知，不编造网络诊断。

**PD-20 SHOULD**：对可恢复失败提供重试、返回编辑、复制脱敏诊断或查看详情。自动重试应有界限；改变持久状态的操作应先确保重试不会重复执行。

**PD-21 MUST**：多成员、批量设备或多实例操作需要表达部分成功，指出失败对象；不能用一条“全部成功”覆盖局部失败。

**PD-22 MUST**：保存或应用失败时说明旧配置是否仍然有效。若确实可能造成远程管理连接中断，应在执行前说明影响并提供适合该功能的恢复方式。

## 6. 安全、信任与风险表达

**PD-23 MUST**：网络密码、凭据、令牌和私钥默认遮蔽；仅通过明确动作临时展示或复制。不得将其放进 URL、统计事件、普通日志、错误提示或默认诊断导出。

**PD-24 MUST**：导出、复制或分享完整敏感配置前说明包含哪些敏感信息；普通诊断导出应默认脱敏。测试和文档使用明确的示例值，不使用真实身份信息。

**PD-25 MUST**：删除持久配置、撤销访问、开放管理接口、改变 ACL 或暴露子网等操作，应清楚标识对象、范围及后果。对难以恢复或会中断访问的操作使用适当确认或可用的撤销机制；不要求所有低风险按钮都增加确认弹窗。

**PD-26 MUST**：不将关闭加密、扩大监听范围、共享网络密码或关闭防火墙作为默认排障建议。需要此类设置时，应解释具体风险并优先提供范围更小的方案。

**PD-27 SHOULD**：用户提供名称、节点返回文本和日志属于不可信内容；呈现时遵循前端输出编码规则，不把远端消息当成 HTML、命令或可信操作指令。

## 7. 跨端一致性、术语与本地化

**PD-28 MUST**：同一个领域概念在 Web、GUI、CLI 和文档中保持一致含义。参考 [命名规范](naming.md)；遇到既有文案冲突，应记录选定词语和兼容影响，不顺手批量改名。

| 概念 | 使用要求 |
| --- | --- |
| 网络 / network | 一组身份及组网配置；不能与单条网络连接互换 |
| 节点 / peer | 组网中的对等参与者；设备和运行实例未必是一一对应 |
| 直连 / P2P、中继 / relay | 表达实际路径，不用“在线/离线”替代路径类型 |
| 网络密码、凭据 | 两种身份机制，文案必须说明当前所指；不得混称登录密码 |
| 虚拟 IP、物理地址、监听地址 | 按用途明确标注，复制、校验和帮助示例使用相同语义 |

**PD-29 MUST**：已接入国际化的端，新增用户可见文案进入适用端的现有 i18n 资源；共享界面补齐中文、英文。独立 uptime 前端尚未接入共享 i18n 时沿用本地方案，本条不隐含要求迁移。变量、数量、单位和状态词应可翻译，不拼接无法调整词序的句子。

**PD-30 MUST**：字节/比特、延迟单位、百分比和速率单位明确且一致；换算集中复用。空值、未知、零值分别处理。诊断时间展示应能确定时区和事件先后。

**PD-31 SHOULD**：复用共享配置和状态组件；差异来自平台能力、屏幕及权限模型，而非各端独立发明语义。平台不支持的能力应解释原因，不能展示可点击但必定失败的主操作。

## 8. 可访问性与响应式交付

以下是对新增和修改界面的要求，不代表现有页面已通过可访问性认证。

**PD-32 MUST**：主要任务能用键盘完成；交互控件具备可访问名称，输入有标签，错误能关联到输入，焦点可见。对话框应正确管理进入、退出和返回焦点。

**PD-33 MUST**：连接状态、告警和校验结果不能仅依赖颜色或图标。异步结果应通过适当的状态区域向辅助技术通知，避免高频轮询不断打断读屏。

**PD-34 SHOULD**：以 WCAG 2.2 AA 的相关条目检查颜色对比、缩放、触控目标及键盘交互；移动端窄屏和长译文下，主操作、重要状态和错误不能被遮挡或裁切。

**PD-35 SHOULD**：表格和网络图提供可读取的节点信息；图形不能成为获取连接状态、路径和关键指标的唯一入口。

## 9. 需求与验收记录模板

对 PD-04 所述变更，将以下内容写入现有 issue、PR 或设计文档即可；内容不适用时说明原因，不额外引入审批流程。
每个独立需求归档到 `process/<需求名称>-<状态>/`，其中 `require/` 保存分析、`plan/` 保存计划、`task/` 保存看板和任务明细；issue/PR 引用对应文档。用户管理、拓扑集成与现有 Web 交互/美化分别维护，依赖通过链接关联，使用 [协作规则](../../process/README.md) 保持编号及状态一致，避免在需求文档重复维护任务状态。

**MUST** 编写或修改上述明细前，先核实相关项目现状与代码，在需求根 `README.md` 更新需求/计划汇总：目标、基线、文档与实现进度、已遇问题/阻塞/待确认项及下一步。详细场景和方案据此展开，现有行为引用代码路径与符号，拟新增行为注明方案状态；未确认的页面表现、能力或接口记录为待核实，不靠推测填满模板。执行中同步汇总，字段与顺序见[汇总模板](../../process/templates/summary.md)及协作规则。

具体计划和任务按单一目标拆为 `plan-<编号>-<名称>.md` 与 `task-<任务编号>-<任务名称>.md`，各自 README 保留目录/看板；公共契约单处维护并引用，不把所有细节重新堆进汇总。

用户要求“需求拆分”时，必须从需求拆到计划、再从计划拆到实际任务文件；强制评估多 Agent 的文件所有权、并行组、前置契约和后续联调。未经取证的体验问题先设核实任务，不能把视觉改进目标写成已发生缺陷。此过程只交付文档，不隐含开始页面开发或运行验证。

仅修改这些需求/计划/任务文档或本规范时，检查目录、链接、编号和状态即可，不安装依赖、不运行构建或测试、不主动触发或等待 CI。下面的行为验收要求适用于实际实现和页面改动，不能因为本次只写需求就宣称已经通过。

```text
用户与场景：谁在什么条件下，需要完成什么任务？
目标与范围：成功的可观察结果；本次不处理的范围。
对象与权限：修改的是哪类配置、实例或设备，谁可以操作？
流程与状态：入口 → 操作 → 反馈 → 成功；加载、空值、过期和部分失败。
异常与恢复：权限拒绝、断网、超时、输入错误、保存/应用失败如何恢复？
安全与兼容：敏感信息、风险操作、旧配置、跨端和语言资源的影响。
验收：Given 前置条件 / When 用户动作 / Then 可验证结果。
验证记录：实际验证的平台、语言、测试命令或人工步骤，以及未验证项。
```

示例：**Given** 已保存网络配置但核心实例尚未启动，**When** 用户点击“启动”，**Then** 在确认实例运行前显示“启动中”；若系统拒绝 VPN 授权，显示未启动及重试入口，保留配置，不出现“已连接”成功提示。

## 10. 提交前自查

- **MUST**：验收说明覆盖本次实际修改的成功路径及至少一个相关失败/边界路径，不能只验证截图或按钮能点击。
- **MUST**：新增的状态逻辑、重试、取消或权限判断有相应行为验证；采用现有自动化测试或可复现人工步骤，明确哪些检查未执行。
- **SHOULD**：涉及界面变化时检查中文、英文、键盘和窄屏；涉及 Web/GUI 共享组件时检查受影响的两个调用端。
- **MUST**：交付说明区分已实现、已验证和后续建议；不能把本规范中的目标当作当前产品已具备的能力。
