## 一、汇总状态与统计边界

**T001：进行中；开发完成 0 / 有效叶子 11。** “0”是本文件目前**尚未逐项完成现行 Task DoD 的证据核销**，**不是代码完成率为 0**。以前已经通过的 Go/Vue/跨仓 CI 可作为复核线索，但需要关联到实际提交与对应完整 Task 验收后才能更新叶子状态。

- **有效叶子**：T001.01～T001.05（5 项）、T001.06.01～.02（2 项）、T001.07～.08（2 项）、T001.09.01～.02（2 项），合计 **11**。汇总节点 T001、T001.06、T001.09 不重复计数，已取消的 T001.10 不计数。
- **状态定义**：待办 → 就绪 → 进行中 → 待评审 → 待验证 → 已完成；实际受阻标「阻塞」，取消标「已取消」。**“待验证”表示存在实现但完整 DoD 尚未核销，不能因为目录/测试存在就标完成**；“就绪”必须满足全部硬依赖和明确开发授权。
- **父级汇总**：全部有效子级已完成才能标完成；全部待办为待办；有效剩余子级全部阻塞为阻塞；其他混合状态为进行中。新建、取消、重开、验证变化时，沿父链更新“完成叶子数/有效叶子数”。`0/0` 不代表完成。
- **需求验收分离**：这里的“已完成”仅指**开发 DoD**；真实 Linux/fnOS、私有 Deploy 或 Sub2API 人工业务验收只在 [R001 的 AT 验收记录](v1-platform-scope.md#5-可测试验收条件) 维护，不能把 CI 通过换算为“已验收”。

## 三、每个叶子 Task 的验收条件（DoD）

下列测试**是必须满足的条件，不是声称已执行成功的结果**。独立验证基线为**当前实际代码 + 已交付的硬依赖**，不得假定其他未完成 Task 会兜底。

| 叶子 Task | 输入、输出与验收要求 |
| --- | --- |
| T001.01 | 空集成启动 → 在本机可信终端初始化管理员 → Web 登录/注销、重启后控制端身份一致；未认证访问和跨站写入拒绝，实际 Go/Vue 测试通过 |
| T001.02 | 登记合法 Git 源并手动刷新 → 原子更新固定版本目录；凭据不出现在客户端；私有 Deploy 可经有权 SSH 授权读取；HTTP 只有显式配置主机白名单和允许开关后方可使用，且不得在明文 URL 内传递凭据；刷新失败保留旧快照 |
| T001.03 | 固定 Git Commit 的合法/恶意 Manifest → 完整 Schema 和跨文件语义检查；商店仅展示合规应用，跨来源不混淆 app_id，变更源码不悄然改变旧固定版本 |
| T001.04 | 可信本机指纹、Agent UUID、一次性码 → 安全配对/身份绑定；错误 SPKI 或 Agent 身份失败、成功重新配对撤销旧授权；浏览器看不到 Token，多主机路由不串线 |
| T001.05 | Agent 完整/不完整/离线及 stopped 容器 → 展示状态、时间戳和资源归属；**保留并明确标记最后一次完整成功快照**，离线/部分结果不覆盖或误删已观察资源，页面重新打开仍能识别数据新旧 |
| T001.06.01 | 已确认来源 ID + app_id + 固定 Git Commit → 内容可追溯且符合 Schema/语义的最小 ZIP、Manifest 摘要与包 SHA-256；不混入运行时 `.env`/`.secrets`、数据目录、额外文件；相同输入的版本身份明确可复核 |
| T001.06.02 | 输入上述固定 ZIP、目标已配对主机 → 经 SPKI/TLS/Token 完整传输、HEAD/PUT 与摘要回执检查，重复上传幂等；网络/授权错误失败关闭；无执行行为 |
| T001.07 | 提交固定 UUID 的受批准安装准备意图 → 控制端可查询/取消当前 Grant 下的 `prepared`，保留请求索引；同 UUID 不同请求冲突、未知响应按原 UUID 查证；资源预检完整性不足时禁止继续；不把准备写成已运行 |
| T001.08 | 准备任务及本机批准 → **在真正执行前**经当前控制端 Grant、来源/包批准、资源锁原子校验；并发撤销和冲突不能绕过；无批准/第三方危险请求不可执行，且接口不提供任意 Shell |
| T001.09.01 | Sub2API 参数和目标主机 → 受控初装任务、UI 状态/恢复、可查询且脱敏的日志、实际 Sub2API/PostgreSQL/Redis 三服务健康检查；失败可诊断且保留现场；本机真实 Docker 验收另见 AT |
| T001.09.02 | 已安装实例 → 受归属约束的更新/卸载，管理员密钥与已有数据不意外重置；卸载默认保留数据，未授权或外部容器不接管，重启与故障恢复后状态正确 |

**共享文件与多 Agent 边界**：同一叶子 Task 由一个主责 Agent 负责完整业务结果；一个需求在同一仓库复用一个工作分支、原则上一个 PR。允许不同 Agent 在隔离工作区实现非冲突任务，最终按依赖顺序合并；`internal/httpapi/`、`internal/storage/`、统一路由及共享模型由同一集成人协调，**不允许并发覆盖**。跨仓契约由各仓库分别维护，引用固定接口/Commit，不在本文件同步外仓任务状态。

## 四、任务依赖 DAG 与可并行批次

```text
T001.01 平台登录
├── T001.02 Git 来源 ── T001.03 Schema/商店 ── T001.06.01 安全固定 ZIP ───┐
└── T001.04 Agent 安全配对 ┬── T001.05 主机资源快照                     │
                          └── T001.06.02 Bundle 交付（同时依赖 .06.01） ───┤
                                                                            ▼
                                                    T001.07 准备任务与恢复 ─ T001.08 运行期安全门禁
                                                                                         │
                                                                                         ▼
                                                                         T001.09.01 首次受控安装
                                                                                         │
                                                                                         ▼
                                                                         T001.09.02 更新与卸载
```

- **可先并行**：在 T001.01 已实际可用且契约稳定的前提下，T001.02 与 T001.04 可分别实现；T001.05 与 T001.03 可在各自前置完成后并行。已经存在的能力优先复用，不重新建设。
- **依赖完成后**：T001.06.02 正式交付须已有固定 ZIP 与可用配对；T001.07 依赖包交付和 Agent 的现有准备协议；T001.08 是后续执行的硬安全门禁；安装和生命周期按顺序集成。
- **必须串行或协调**：`host_id`/Agent 身份、部署包摘要、任务状态机、资源锁与共享 SQLite schema 的修改；跨仓需要固定版本契约并各自验证。
- **阻塞事项**：真实私有 Deploy 的运行机授权、Agent 真正 `/v1/tasks` 执行器、Sub2API 脚本与配置安全初始化、实际 fnOS/Docker 占用及目录行为。只有确实阻止当前 Task 的硬依赖才标阻塞；人工验收若只是发布门槛，不能无故阻断不依赖它的开发。
