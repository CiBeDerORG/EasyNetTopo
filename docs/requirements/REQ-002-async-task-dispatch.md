# REQ-002：GitHub 构建成功 Hook 与两级异步任务调度

状态：第一期开发中（分支 `feat/async-host-app-tasks-20261108`）  
范围：EasyNetTopo 控制端及主机商店现有应用更新接口。  
原则：**跨主机并发、同主机串行；接口只做校验及任务落库，不等待更新完成。**

## 一、目标

- GitHub Actions 在镜像推送成功后发送 Hook；不传镜像版本号。
- 使用目标服务的 deploy 配置，调用现有更新脚本拉取配置指定的最新镜像/版本（A 方案）。
- 每次调用可以指定多个不同主机与服务，也允许一个主机包含多个服务。
- EasyNetTopo 创建「主机任务（HT）」和「应用任务（AT）」两级执行记录。
- 每台主机一次只运行一个应用更新；不同主机可同时更新。
- 主机和应用卡片均展示任务号、实时状态、触发来源。
- **成功完成后**隐藏任务号及任务状态，展示最近完成时间；失败或中断仍显示任务信息。

## 二、Hook 协议

`POST /api/hooks/deploy/update`

`Authorization: Bearer <HOOK_TOKEN>`

```json
{
  "trigger_source": "github_actions",
  "targets": [
    {"host_name": "Mac-mini", "service_name": "app-a"},
    {"host_name": "Linux-server", "service_name": "app-b"},
    {"host_name": "Mac-mini", "service_name": "app-c"}
  ]
}
```

**环境变量：** `EASYNETTOPO_HOOK_TOKEN`（至少 32 字符，建议在反向代理中仅对 HTTPS 暴露此接口）。未配置时接口返回 503。GitHub Actions Secrets 中保存相同 Token；切勿提交到仓库。

**验证：** 目标数量 1–64、JSON 严格字段、合法来源字符串、主机必须存在且已配对、主机名称唯一、服务名称唯一匹配受信任应用源的 `app_id` 或展示名称。一个请求内重复的同一主机/服务只创建一次任务。匹配失败返回 422，不创建部分任务。

**响应：** HTTP 202，包含 `accepted: true` 与新创建的 HT/AT 任务列表（均为 `queued`）。202 只代表任务已持久化，不代表部署已经成功。HTTP 请求期间不调用远程 Agent。

## 三、手动更新与状态接口

- 现有 `POST /api/v1/hosts/{host_id}/apps/update` 也进入同一队列；仍需管理员登录、同源标记与可信来源 revision。
- `GET /api/v1/tasks` 由管理员读取近期任务，供前端展示。
- `trigger_source` 对 Hook 由调用方传入，对手动更新由服务端固定设置为 `manual`，防止伪造手动来源。

当前第一期将**普通应用更新**纳入队列；安装、卸载、强制更新、Agent 自更新仍沿用旧接口与原有安全约束。这些旧操作如遇 Agent 忙会被拒绝，不绕过 Agent 独占锁。

## 四、任务结构

SQLite 在现有控制端数据库新增 `execution_tasks` 表，非独立部署组件。

- **主机任务**：一个 HTTP 请求针对一台主机的批量操作，对应一个 HT 任务。
- **应用任务**：每个 HT 下有一个或多个 AT 任务，记录应用来源、`app_id`、动作、来源、当前状态和时间。
- 对同主机不同请求，按任务入库顺序串行，不允许多份 Hook 并行越过主机互斥。
- 对不同主机，调度器启动独立工作 goroutine，并行准备包、传输与远端轮询。
- 工作器等到 Agent 返回 `succeeded` 或 `failed` 等最终状态后，才调度同主机下一应用。
- 子任务失败不终止其他应用；父任务任一子任务失败则失败；全部成功则成功。
- 控制端记录 `created_at`、`started_at`、`finished_at`、`trigger_source`。不保存 HTTP Token、脚本输出或 Secret。

## 五、状态与故障恢复

- `queued`：待分配；`preparing`：生成已验证的候选包并传送；`running`：更新命令可能已发送；`succeeded` / `failed`：完成；`interrupted`：无法安全确认。
- 控制端重启后，尚未发执行指令的 `preparing` 恢复为待执行；`running` 不直接重新发命令，而是轮询 Agent 现有执行状态。
- 主机离线时，不将网络异常直接误判为更新失败，也不继续同主机后续任务。
- Agent 当前只记录应用动作/结果，**没有每次操作的独立远端任务 ID**。如果重启后无法辨认结果，必须标记中断，避免把历史结果误认为本次成功或重复执行。
- 当存在 `interrupted` 的子任务时，该主机后续更新保持等待人工排查，避免交叉写入同一 Compose 项目。

## 六、界面约定

- 主机卡片展示选中主机当前 HT：排队/准备/执行中时显示编号、来源及状态。
- 应用卡片展示其 AT：排队/准备/执行中显示编号、来源及状态。
- 执行**成功**后，不再展示任务状态/编号，仅展示完成时间（本机时区）。
- 执行失败/中断时显示编号、错误信息，便于排查。
- 应用原有 Docker 运行状态（运行中/停止等）继续独立存在，不得混同为「更新任务」状态。

## 七、第一期不做

- 不做 Redis、RabbitMQ、独立任务服务器、分布式数据库。
- 不引入新的 Docker 部署引擎，不让 GitHub 接触 Agent 地址。
- 不在 Hook 请求体传镜像 URL、脚本内容、系统命令或版本号。
- 不为 EasyHostAgent 增加数据库；Agent 继续使用已有应用状态记录。
- 不提供未经确认的自动重试执行，以免错误重放产生副作用。

## 八、需要覆盖的验收用例

1. A 主机两个服务与 B 主机一个服务一次提交：生成 HT×2 + AT×3，A 串行 B 并发。
2. 多个 HTTP 请求连续指定同一主机：按创建顺序排队，不触发 Agent 409 异常覆盖。
3. Hook 立即 202；最终状态由 GET /api/v1/tasks 查询。
4. 模拟任务失败：同主机后续应用继续执行，父任务结束为失败。
5. 模拟控制端重启：`preparing` 可恢复；`running` 不重复发更新指令。
6. 主机和应用在执行中展示编号与 `GitHub Actions`；成功后只显示最近完成时间。
7. Token 缺失/不匹配、主机重名/不存在、服务重名/不存在，均不创建部分任务。
